刚好够用：我如何让 Kilo Code 和 Codex 协作

发表于2026-09-14|更新于2026-09-15|AI应用
|总字数:1.4k|阅读时长:4分钟|浏览量:

我以前探索过不少 AI 编程工具：Claude Code、Pi、OhMyPi、ZCode、Qoder、Trae、DSH 等都尝试过。

但现在回头看，我越来越觉得，重要的不是工具越多越好，也不是自己使用过多少工具，而是找到一组刚好够用的工具。

目前对我来说，Kilo Code 和 Codex 已经足够支撑大部分开发工作。它们不是二选一的关系，而是可以协作完成同一个任务的不同阶段。

让 Kilo Code 负责清晰、快速地推进

它对我最大的价值，是我可以比较清楚地看到 Agent 在运行时做了什么：它如何拆分任务、调用子智能体、修改文件、执行命令，以及当前处于什么状态。

这种过程的可见性，让我可以跟着它一起思考：

  • 它对需求的理解是否正确？
  • 现在的实现方向是否符合我的预期？
  • 它有没有扩大任务范围？
  • 当前方案是否值得继续推进？
  • 哪些地方需要立即纠正？

如果遇到不懂的地方，我可以马上询问；如果发现方向不对，也可以及时修正。它不一定因此就能自动把任务做好，但我能够更早发现问题，而不是等到最后才面对一个已经偏离目标的结果。

尤其是在需求还不够明确的时候，我更倾向于使用 Kilo Code。它的交互比较清晰、反馈比较快速，我可以一边看它执行，一边补充自己的思考，让需求、边界、技术选项、功能定义和职责划分逐步收敛。

让 Codex 负责复杂任务和最终验证

我会根据任务的风险来判断是否需要 Codex 参与。

我通常会考虑：

  1. 最终结果是否必须严格验证；
  2. 这个结果是否容易验证；
  3. 任务会牵扯项目中的多少部分；
  4. 局部修改是否可能影响其他模块。

如果任务涉及范围比较大，跨越多个模块，最终效果又不容易验证，我会更倾向于使用 Codex。

比如网页功能、功能扩展、架构升级，以及需要同时考虑上下游影响的改动。这类任务不是简单地“把代码写出来”就结束了，还要确认修改是否完整，是否破坏原有逻辑，最终结果是否真正符合预期。

但我一般不会让 Codex 在需求模糊的时候替我做全面分析。它有时会沿着一个大概目标不断发散，输出大量内容。那些内容可能有价值，但真实使用时往往很难阅读和消化。

如果方向本身还没有确定，Codex 分析得越认真，反而越容易把问题做复杂，让项目距离真正完成越来越远。

所以，我更愿意先用 Kilo Code 把问题讲清楚、把方向收敛下来，再让 Codex 接手已经明确的复杂任务。

Agent 越认真，不一定离目标越近

我自己遇到过一种很典型的情况：一开始并没有想清楚到底要解决什么问题，就直接让 Agent 开始推进。

需求边界没有确定，技术选项没有比较，功能也没有定义清楚，模块职责更没有划分好。结果就是代码虽然不断增加，但整体方向越来越混乱，脑袋几乎要炸了。

最后，我不得不从头梳理，把大约 90% 的链路和设计重新弄清楚。

这件事让我意识到，如果问题本身没有定义清楚，那么 Agent 越认真，可能越会把错误方向做得完整。它不是没有工作，而是在非常努力地把一个还没有想明白的问题继续扩大。

因此，在 AI 编程时代，跟着 Agent 思考并不是一种额外技巧，而可能是项目能够达标的必要路径。

如果只是给 Agent 一个模糊目标，然后等待它交付最终结果，很多问题会在最后才暴露。而到了那个时候，问题往往已经从“改一个函数”变成了“重新梳理整个链路和设计”。

不是选择，而是协作

现在我的工作方式大概是：

  • 用 Kilo Code 推进需求和代码；
  • 在执行过程中观察它的思路和状态；
  • 及时询问、判断和纠正方向；
  • 让需求、边界和职责逐步明确；
  • 对已经明确、但影响范围大或难以验证的任务，让 Codex 负责实现和验证；
  • 如果方向仍然模糊，就暂停编码，回到问题定义和架构设计。

所以，这不是“Codex 还是 Kilo Code”的问题，而是如何让它们协作。

Kilo Code 更适合清晰、快速地交互，让我能够跟随过程并收敛需求；Codex 更适合在方向已经明确之后，处理复杂链路和需要验证的任务。

以前探索很多工具，是为了寻找最好的工具。现在留下这两个，是因为它们已经构成了一个刚好够用的组合。

工具不在于多，而在于是否真正匹配自己的工作方式。

真正重要的，也不是使用过多少 AI 编程工具，而是能不能跟着 Agent 一起思考，知道什么时候该继续推进，什么时候必须停下来重新定义问题。
